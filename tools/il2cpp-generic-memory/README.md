# IL2CPP のジェネリックのメタデータの最適化: 索引

IL2CPP の Player は、ジェネリック型の具象型（`List<Foo>` など）を使うたびに、VM のメタデータ（クラス、メソッド、表）を積む。この作業は、それを「使う時まで作らない」「作る数を減らす」ことで減らす。このファイルは、関係するファイルがどこにあって何をするかの索引である。

- ブランチ: メモリの最適化は `il2cpp-generic-memory`、速度の最適化は `il2cpp-speed`（メモリのブランチの上に積む）。
- Unity 6000.3.20f1。動かして確かめたのは Windows x64 と、Android の実機（arm64、Pixel 3 XL）の IL2CPP の Player。iOS では動かしていない。
- 2026-11-11 までの計測の記録と、採らなかった手法の説明は [record.md](record.md)（数値と「ファイル」の表は古い）。Editor を使わないビルドの手順は [offline/README.md](offline/README.md)。

## どこに何があるか

| 場所 | 役割 | Player に入るか |
|---|---|---|
| `Assets/Il2CppLazyMetadata` | **製品。** libil2cpp を「使う時に作る」ように変えるパッチ | iOS のビルドで自動で当たる |
| `Assets/UniTaskStateMachinePool` | **製品。** UniTask の async のステートマシンを寄せる ILPostProcessor | UniTask を使うアセンブリのコンパイルで走る |
| `Assets/Tests/GenericMemory/Editor` | 検証。計測用 Player のビルドと、IL を書き換える段階 | 段階を指定したビルドでだけ走る |
| `Assets/Tests/GenericMemory/Scenario` | 検証。計測用のアセンブリ（パターン、検証、ベンチ） | `GENERIC_MEMORY_SCENARIO` を定義したビルドだけ |
| `tools/il2cpp-generic-memory` | 道具。ビルド、実行、集計のスクリプト | 入らない |
| `tools/il2cpp-generic-memory/.local`、`results` | 作業用。il2cpp フォルダの複製、保存した入力、計測の生の結果 | Git に入れない |

## 製品のコード

### `Assets/Il2CppLazyMetadata/Editor`

| ファイル | 中身 |
|---|---|
| `Il2CppLazyMetadata.cs` | `OnPostprocessBuild` が iOS のビルドの後に Xcode プロジェクトの中の libil2cpp を書き換える。本体は `Apply(root, switched)`。差し込みは「元の文面 → 新しい文面、何回あるはずか」の並び（`Swap`／`Before`／`After`／`Every`）で、`Edit` が回数を確かめ、合わなければビルドを止める。2 度当てても変わらない |
| `Native~/Il2CppLazyMetadata.h` | libil2cpp/vm へ複製するヘッダー。ジェネリックの具象型のメソッド・プロパティ・イベントを使う時に作る処理と、RGCTX の項目を読まれた時に解決する処理 |
| `Native~/Il2CppLazyInterfaces.h` | 同じく複製するヘッダー。インターフェースの vtable スロット、インターフェースのクラス、配列のメソッドの表を使う時に作る処理。表の項目の下位 2 ビットを印に使う（冒頭のコメントに表がある）。表を読む側は全部 `il2cpp::vm::LazyInterfaces` を通る |
| `Native~/Il2CppCastCache.h` | **速度のための変更**（`il2cpp-speed` ブランチ）。インターフェースへのキャストの答えと、変性でしか実装していないインターフェースのスロットの場所を、固定の表 2 つ（各 64 KB）に覚える。読む側はロックを取らない |

- `switched` が偽（製品）なら常に遅延する。真なら実行時の環境変数で切り替える形になり、計測用のカウンタ（`libil2cpp/GenericMemoryCounters.h`）が要る。
- ビルド時に環境変数 `IL2CPP_LAZY_METADATA=0` を置くと、パッチを当てない。
- ビルド時に環境変数 `IL2CPP_CAST_CACHE=0` を置くと、キャッシュだけを外す。差し込みの行は残り、ヘッダーの先頭の定義でコンパイル時に消える。前に書き換えたフォルダをもう一度ビルドした時も、その時の指定に従う。
- `Native~` は Unity が読み込まないフォルダで、ヘッダーは C# がファイルとして読んで複製する。

| `metadata/CustomAttributeDataReader.cpp` | 属性の名前つき引数がプロパティの表を読む前に作る |

| `Verifier.cs` | 書き換えた本体を書き出す前に確かめる（名指ししたメンバーが見つかること、スタックの深さ） |
| `Il2CppLazyMetadataCheck.cs` | ビルドせずに、パッチがこの Editor の libil2cpp に両方の形で当たり、2 度当てても変わらないことを確かめる |

IL の段階:

| 段階 | 何をするか | 型の同一性 |
|---|---|---|
| `comparers` | 型を見る所が既定の比較子だけのメソッド（`List<T>.Contains` など）を `object` の文脈で呼ぶ。`canon` を含む | 変えない |
| `enum` | foreach の列挙子など、メソッドの中でしか見えない構造体のローカルを `List<object>.Enumerator` にする | 変えない |
| `linq` | `List` と配列から始まる LINQ の連鎖を、内部だけ `object` で動かす | 利用者から見える値は変えない |
| `canon` | 型引数を見ないジェネリックメソッドを `object` で呼ぶ | 変えない |
| `free` | 型引数を見ないメソッド（`Count`、インデクサなど）を `List<object>` の文脈で呼ぶ。`list[i]` が遅くなるので採っていない | 変えない |
| `hoist`、`hoistall` | ジェネリッククラスのメソッドを型の外の静的メソッドへ移す。VM の遅延化があれば上積みがない | 移したメソッドがリフレクションで元の型から見えなくなる |
| `async`、`unitask` | UniTask のステートマシンを寄せる（製品の ILPostProcessor の元になった試作） | — |
| `nulltest` | エンジンのオブジェクト（`UnityEngine.Object`）と `null` の比較、`if (x)` を、その場で答える。メモリではなく速度のための段階（下の「速度の最適化」） | 変えない |

VM の遅延化に重ねる採用案は `comparers+enum+linq`。`enum` は `hoist` より前に置く。

## 測り方の決まり

- **基準**: パッチを当てていない動き。計測用の libil2cpp でスイッチを全部切った時と同じ。
- **単位**: 型 1 つあたりの、メタデータのプールに要求されたバイト数。パターンを 2 つの数で実行し、その差から出す。
- **組**: スイッチの桁の並び。1 桁目がメソッド、2 桁目が RGCTX、3 桁目がインターフェースのスロット（配列のメソッドの表を含む）、4 桁目がインターフェースのクラス、5 桁目がキャストのキャッシュ。`1111` がメモリの遅延化を全部オン、`11111` がキャッシュもオン、`110` が 2026-11-11 までの形。
- **ラベル**: `Logs/UnityTests/GenericMemory/<ラベル>` にある Player。計測の結果は `results/<名前>`、検証の結果は `results/checks`。
- 計測用の Player は、結果を書いてからプロセスが消えるまで 20〜55 秒かかる。`m-run.py` と `c-bench.py` はそれを待たない。
- 速度は、ほかのビルドや計測が動いていない時に測る。プールのバイト数は決定的なので、並行でもよい。

## 最終結果: 古い端末で、元のコードを変えずにどこまで上がるか（2026-11-14、Pixel 3 XL）

2018 年の端末（Pixel 3 XL、Snapdragon 845、Android 12、画面は 60 Hz）で、C# のソースを変えずに、ビルド後の加工とコンパイラの指定だけでメモリと速度がどこまで動くかを、同じ日に同じ端末で測り直した。

- **重ねたもの**: (1) libil2cpp の遅延化のパッチ（メモリのブランチ）、(2) キャストのキャッシュ（速度のブランチ）、(3) IL の段階 `comparers+enum+linq+nulltest`、(4) コンパイラの指定 `-O2` と `-flto=thin`。
- **入れ方**: Android では、(1)〜(3) を検証用の経路で入れた。パッチを当てた il2cpp フォルダの複製を `UNITY_IL2CPP_PATH` で使わせ、IL の段階は計測用のビルドで指定した。製品のパッチが自動で当たるのは iOS だけで、iOS では動かしていない。(4) は `PlayerSettings` の追加の引数だけで、パッチとは関係なく使える。
- **測ったもの**: ゲームに近い負荷のサンプル（`LocalWorkload`、リポジトリの外。下の「ゲームに近い負荷での計測」）と、計測用の Player のカーネル。条件を交互に走らせ、同じ巡のパッチなしとの比で読む。サンプルは 6 本の Player を 3 回に分けて測り、どの回にもパッチなしを入れた。
- **確かめたこと**: サンプルののべ 122 回の実行で、状態のチェックサムと出来事の数が、体数ごとに全部一致した。計測用の Player は、パッチなし、遅延化だけ、全部入りの 3 本で検証 6 種が通る（速度のブランチのランタイムの 1 本は、検査を直した時に通してある）。計測中に、温度による周波数の制限は一度もかからなかった。ビルドの指定は、全部のコンパイル単位に付いたことをビルドの記録で確かめた。
- 結果の場所: サンプルは `.local/w/results/w-b-*`、`w-c-*`、`w-d-*`。計測用の Player は `results/e-rows`、`results/e-max`。

### 結論

**メモリを減らすのは遅延化のパッチで、ゲーム全体の速度を上げるのはコンパイラの指定だった。** 2 つは別々に効き、重ねられる。キャストのキャッシュと IL の段階は、特定の操作を大きく速くするが、サンプル全体の時間は動かさない（パッチの検査の費用をほぼ打ち消す所まで）。

| 行き先 | 入れるもの | プロセスのメモリ | シミュレーションの時間 | 60 fps を割る規模での FPS | libil2cpp.so | ビルド時間 |
|---|---|---:|---:|---:|---:|---|
| メモリを取る | 遅延化のパッチ | −9.3 MB（−4.1%） | +1.0% | −0.9〜−1.1% | +7.5% | 変わらず |
| 速度を取る | `-O2` と `-flto=thin` | −0.6 MB（−0.2%） | −6.1% | +5.9〜+7.9% | +20.3% | 約 1.4 倍 |
| 両方 | (1)〜(4) の全部 | −9.7 MB（−4.2%） | −5.1% | +4.5〜+6.0% | +26.5% | 約 1.5 倍（計測用の Player では 2.3 倍） |

- 型あたりのメタデータで見ると、遅延化は 16 パターンのうち 9 つを 60% 以上、IL の段階を重ねると 13 を 60% 以上減らす（下の表）。
- 60 fps を保てている規模（このサンプルで 1,500 体まで）では、どの構成も 59.9 fps で、差が出ない。
- ThinLTO を入れた時も、パッチの費用は残る。同じ ThinLTO どうしで比べると、全部入りはパッチなしよりシミュレーションが 1.5%（描画なし）〜3.2%（3,000 体、描画つき）遅い。`-Os` どうしの +1.0% より小さくはならない。

### 新しい端末での予想（計測ではない）

新しい端末では測っていない。手元にある「コアが変わると何が変わるか」の実測は 2 つだけである。(a) この端末の小さいコア（Cortex-A55、順番どおりに実行する）と大きいコア（Cortex-A75）での、RGCTX の読み出しの単体の試験。コンパイラもコードも同じ。(b) PC（幅の広いコア、ただしコンパイラは MSVC）と A75 での、同じカーネルの比。

| RGCTX の読み出しの単体の試験（`-Os`、製品の形） | A55 | A75 |
|---|---:|---:|
| ループ、パッチなし → パッチあり（1 項目あたり ns） | 12.35 → 13.42（+1.07、+9%） | 3.13 → 3.78（+0.65、+21%） |
| 渡すだけのメソッド | 11.04 → 13.39（+2.35、+21%） | 3.02 → 4.53（+1.51、+50%） |

| 項目 | 予想 | 根拠と限界 |
|---|---|---|
| メタデータのバイト数 | 変わらない | Windows x64 と Android arm64 で、16 パターンとも同じ値だった。64 ビットの構造体の大きさで決まり、コアには依らない |
| プロセスのメモリの削減（MB） | 同じ程度。端末のメモリに対する重みは下がる | 減る量は使うジェネリックの数で決まる。ページの大きさが 16 KB の端末では測っていない（データなし） |
| キャストのキャッシュ | 倍率は保たれ、減る ns は小さくなる | 遅延化 → キャッシュの倍率が、A75 で 2.6／7.3／13 倍、PC で 2.6／7.2／12 倍とほぼ同じ。減る ns は PC で A75 の 4 割 |
| null 比較の展開 | 倍率が下がる | A75 で 5.3 倍（10.3 → 1.95 ns）、PC で 3.2 倍（2.99 → 0.94 ns）。消えるのは呼び出し 3 段で、幅の広いコアは呼び出しが安い |
| 遅延化の検査の費用 | 1 回あたりの ns は下がるが、割合は下がらない（上がる向き） | 上の表。A55 → A75 で、ns は 4 割減り、割合は 2 倍あまりになった。周りのコードが速くなるほど、検査の割合が大きく見える。ThinLTO で周りを速くした時も同じ向きだった（+1.0% → +1.5〜3.2%） |
| ThinLTO の得 | 分からない | 別のコアでの実測が無い。呼び出しを消す種類の得なので、null 比較と同じく倍率は下がると推測するが、測っていない |
| 型の初回利用、起動 | 分からない（減る仕事の量は同じ） | この端末でしか測っていない |
| FPS で見える差 | 見える場面が減る | この端末でも、60 fps を保てている間は差が出なかった。同じ負荷なら、速い端末ほど予算に収まる範囲が広い。120 Hz では予算が半分になるので、その分は戻る。新しい端末が何倍速いかは測っていない |
| ライブラリの大きさ、ビルド時間 | 変わらない | 端末に依らない |

まとめると、**メモリの削減は端末が新しくても同じ量だけ得られ、速度の得は絶対値（ns、ms）では小さくなる。** 割合では、キャストは保たれ、呼び出しを消す種類は縮み、パッチの検査の費用はやや大きく見える方向である。効果が一番はっきり出るのは、今回のような古い端末、メモリの少ない端末、60 fps を保てていない場面である。

## 結果の要約（2026-11-12、Windows x64）

|---|---|---|
| 基準 | — | 34.9 KB |

- 届かないのは、Task、UniTask、デリゲートのパターン。
- 代償: 共有コードが RGCTX を読むたびに検査が 1 つ入る。ジェネリックなインターフェースへのキャストと、変性つきのインターフェース呼び出しが遅くなる（Windows での値。Android の実機では、ジェネリックなキャストはパッチなしより速く、遅くなるのは変性つきの呼び出しと一部のジェネリックでないキャストだった。上の「最終結果」）。インターフェースを初めて呼ぶたびに対の表を複製する。`linq` は LINQ の 1 回あたりの GC のバイト数を 1〜7% 増やす。
- **RGCTX の検査の代償は、ゲームに近い負荷では全体に効く。** 2,000 体の AI のサンプルで、製品のパッチはシミュレーションの時間を 6〜11% 増やしていて、そのほぼ全部がこの検査だった。検査の形を直して、このサンプルでの差は雑音の幅（約 1%）になった（下の「ゲームに近い負荷での計測」）。
- `Type.GetInterfaces()` の並び順が変わる（中身は同じ）。

### Android の実機（2026-11-12、Pixel 3 XL、arm64、Android 12）

- 製品と同じ形（常時オン）のパッチ入り libil2cpp は、Unity の Android ビルド（NDK の clang）でコンパイル・リンクできる。
- 検証 5 種が、常時オンと、常時オン＋IL の両方で通る。型あたりのメタデータは、16 パターンとも Windows と同じ値だった。
- 競合の検査（複数スレッドが同時に型を初めて使いながらリフレクションで走査する）の失敗 / 競合の回数:

| ランタイム | arm64 | 備考 |
|---|---:|---|
| パッチなし | 2 / 6,839 | 素の libil2cpp にある競合。内訳が取れた 1 回は、`List<T>` のインターフェースが 8 個中 1 個しか列挙されなかった。Windows でも PC に負荷をかけると 300 回の実行で 39 回失敗し、1 回クラッシュした |
| 常時オン | 0 / 14,447 | |
| 常時オン＋IL | 5 / 200,673 | 5 回とも、プロパティの名前が一瞬 `null` で返ったもの（下の説明）。ランタイムの競合ではなかった。読み直して比べるようにしてからは 0 / 37,440 |

- 常時オン＋IL の失敗は、クラスライブラリ（Mono の BCL）の `RuntimePropertyInfo` が原因だった。名前や getter をランタイムから取った結果を自分の中に持ち、取得済みの印を別のフィールドに立てるが、その間にロックもバリアもない。書いた順を保たない arm64 では、別のスレッドが印を先に見て、まだ `null` の名前を読むことがある。個数は同じで名前だけが違う一覧になり、失敗はどれもプロパティの一番多い `Dictionary<T,int>` で出ていた。x64 では起きない（同じ形の Player で、負荷をかけた 21 万回の競合で 0 回）。libil2cpp にもこのパッチにも関係がなく、パッチなしでも同じコードである。
- 検査は、名前が `null` なら読み直した値で比べ、その回数を結果の `cacheRaces` に書く。読み直すようにした版は、37,440 回の競合で失敗 0 回、`null` を見たのは 2 回だった。パッチなしのランタイムでも、58,383 回の競合で `null` を 1 回見た（失敗は 0 回）。`-generic-memory-propname` は、この競合だけを、ジェネリックも型の初回利用もなしで回す。
- 途中で「ジェネリックの具象型のフィールドの表が、バリアなしで公開されている」ことを原因と見てバリアを 2 か所足したが、足した版でも同じ頻度で失敗したので取り消した。
- 製品のパッチ（`Il2CppLazyMetadata.cs`）が自動で当たるのは iOS だけである。Android では、パッチを当てた il2cpp フォルダの複製を `UNITY_IL2CPP_PATH` で使わせて確かめた。

### エンジンのオブジェクトの null 比較の展開（段階 `nulltest`、`NullTestExpander.cs`）

`UnityEngine.Object` の `x == null`、`x != null`、`if (x)` は演算子の呼び出しで、その先が 3 段の呼び出し（`CompareBaseObjects` → `IsNativeObjectAlive` → `GetCachedPtr`）になっている。il2cpp はファイルをまたいでインライン化しないので、どれも実際の呼び出しになる。答えは「参照が null か、オブジェクトのエンジン側が無くなっている（`m_CachedPtr` が 0）」である。

- **すること**: `UnityEngine.CoreModule` にクラス `UnityEngine.GenericMemoryNullTest`（`IsNull` と `IsAlive`、インライン指定つき）を足し、右辺が `null` のリテラルの比較と、bool への変換を、そこへ向け直す。il2cpp はインライン指定のあるメソッドの複製を、呼ぶ側のファイルごとに書く。
- **元のまま残す形**: オブジェクト同士の比較、`null` が左にある比較、`null` と演算子の呼び出しの間に別の経路が合流する比較。エンジンのモジュール（`UnityEngine.*Module`）の中の比較にも触れない（`CoreModule` に書くのは足したクラスだけ）。
- **数**: リンク前の全コードで、比較 1,834 か所と変換 159 か所を書き換え、220 か所を残す。Player に入るコード（リンカーが削った後）では、1,123 か所のうち 1,002 か所。
- **版が変わった時の止め方**: 演算子と、その下の 3 つのメソッドの本体を、段階を書いた時の形（6000.3.20f1）と照らす。1 つでも違えば、何も書き換えずにビルドを止める。
- **クラスを別にした理由**: 判定のメソッドを `UnityEngine.Object` に置くと、このクラスに静的コンストラクタがあるので、比較のたびに「静的コンストラクタが済んだか」の確認（読み出し 2 つと分岐 1 つ）が残る。
- **注意**: 足したクラスは `UnityEngine.Object` の非公開フィールドを読む。il2cpp はフィールドの公開範囲を見ないので通る（Android と Windows でビルド済み）。

確かめたこと（Windows x64、2026-11-13）:

- `NullTestChecks`（26 件）が、段階なしの Player 3 本と、段階ありの Player 2 本（単独、採用済みの `comparers+enum+linq` との重ね）で通る。期待する答えは固定で書いてあるので、段階なしで通ることが「期待値がエンジンの演算子と合っている」、段階ありで通ることが「書き換えが同じ答えを返す」の確認になる。破棄済みのオブジェクト（参照は null でなく、演算子は null と答える）を含む。
- 既存の検証 5 種が、段階ありの 2 本で通る。

速度（Windows x64、条件を交互に 15 回、最良値、ns）:

| | 段階なし | `nulltest` | `comparers+enum+linq` | 3 つに `nulltest` を重ねる |
|---|---:|---:|---:|---:|
| `objects[i] != null`（`null.before`） | 2.99 | 0.94 | 2.99 | 0.95 |

Android（arm64）:

## ゲームに近い負荷での計測（2026-11-13、Windows x64）

小さいカーネルではなく、ゲームらしいコード全体での差を見た。負荷は `LocalWorkload` というサンプルで、**リポジトリには入れていない**（`Assets/LocalWorkload` にあり、`.git/info/exclude` で外してある。計測のスクリプトと結果は `.local/w/`）。

- 中身: 2,000 体のエージェント（4 陣営、分隊、役割 4 種）が、知覚、状態の判断、A* の経路探索、操舵と衝突、戦闘、復活を回す。MonoBehaviour、マネージャー、インターフェース、ジェネリックのコレクション、利用者が書いたジェネリッククラス（空間ハッシュ、プール）で書いてある。乱数の種と固定の時間刻みで毎回同じ動きになり、最後に状態のチェックサムを出す。
- 測り方: 描画なし（`-batchmode -nographics`、シミュレーションだけ）、ウォームアップ 300 フレームの後の 1,800 フレーム。条件を交互に 8〜10 回、実行の間に 6 秒の休止。値は「シミュレーション 1 フレームの平均」。同じ条件でもラウンドごとに ±10% 動くので、同じラウンドのパッチなしとの比の中央値と、最良値の両方を見る。

**動きは変わらない。** パッチなし、遅延化、キャストのキャッシュ、IL の段階（`comparers+enum+linq`、`nulltest`）、遅延化のスイッチの組み合わせの、のべ 260 回あまりの実行で、チェックサムと出来事の数（キル、経路探索、弾の命中など）が全部一致した。

**製品のパッチは、シミュレーションを 6〜11% 遅くしていた**（検査の形を直す前の値。直した後は下の節）。

| | パッチなし | 遅延化だけ（製品） | 遅延化＋キャッシュ（製品） |
|---|---:|---:|---:|
| 1 フレームの平均、最良値（ms） | 5.81 | 6.29 | 6.16 |
| 同じラウンドのパッチなしとの比 | — | +10.9% | +7.5% |
| ピークのワーキングセット（MB） | 135.2 | 127.3 | 127.3 |

- キャストのキャッシュは、インターフェースへのキャストが多い所（戦闘）を、パッチなしより 4〜7% 速くする。
- IL の段階は、この差を変えない。`nulltest` の効果（null 比較 1 回あたり約 2 ns）は、この規模では見えない。

**原因は、生成されたコードが RGCTX を読むたびに通る検査である。** 遅延化を実行時に切り替えられるランタイムで、同じバイナリのまま測った（最良値、ms。かっこ内は同じラウンドのパッチなしとの比）。

| | 検査あり | 検査なし（`il2cpp-codegen.h` の読み出しを元に戻す） |
|---|---:|---:|
| 遅延化を全部切る | 6.35（+11.6%） | 5.92（+1.8%） |
| 遅延化を入れる（検査なしの方は RGCTX 以外の 3 つ） | 6.42（+12.6%、キャッシュも） | 5.80（+1.4%）、キャッシュも入れて 5.88（+0.9%） |
| `GameAssembly.dll` | 36.12 MB | 34.07 MB（パッチなしは 34.02 MB） |

- 遅延化を全部切っても、検査のコードがあるだけで遅い。入れても、それ以上は遅くならない。代償は「使う時に作る」動作ではなく、検査が実行経路にあることから来ている。
- 検査を外すと、残りの 3 つの遅延化（メソッド、インターフェースのスロット、インターフェースのクラス）とキャッシュを入れても、パッチなしとの差は 1〜2%（雑音の幅）になる。このランタイムでのワーキングセットの削減は、全部入りで −9.6 MB、RGCTX の遅延化を切っても −7.8 MB 残る。
- 検査は、読み出しごとの「項目が空か」の比較と、空の時の関数呼び出しである（`il2cpp_lazy_rgctx_entry`）。参照型のジェネリックは 1 つのコードを共有し、その中から別のジェネリックのメソッドを呼ぶたびに RGCTX を読むので、利用者が書いたジェネリッククラスの内側のループに毎回入る。読み出しは全体で約 20 万か所ある。
- 検査なしの形は、RGCTX の遅延化を切った時だけ正しい。そして RGCTX の遅延化は、メモリの削減のおよそ半分を担っている（`List` を使うパターンで、ありが −83%、なしが −48%）。外すのではなく、検査を軽くする形を考える必要がある。
- **この節の値は Windows x64 と MSVC でのもの。** コンパイラが違えば検査の費用も違う。arm64（Android の実機、clang）で測ると、同じサンプルでの代償は +2.0% だった（下の「端末での計測」）。iOS では測っていない。描画つきの実行ではラウンドごとのばらつきが大きく、差は同じ向きだが数値は出していない。

### 検査を軽い形に書き直す（2026-11-13、メモリのブランチにも入れた）

検査は「項目をメモリの上で比べ、空なら解決し、もう一度読む」形だった。機械語で見ると、費用は比較そのものではなく、その形にあった。

- **MSVC**: 読み手の関数（`il2cpp_rgctx_method` など）が、一部の呼び出しでインライン化されなくなっていた。サンプルの空間ハッシュの検索の関数では、読み出し 10 か所のうち 4 か所が実際の関数呼び出しだった。インライン化された所でも、比べるためと使うためで、同じ項目を 2 回読んでいた。
- **clang（arm64）**: 2 回は読まない。`-Os` では、空の時の呼び出しのためにレジスタを余分に使っていた。

直した形は「項目を 1 回読んで値で渡す。空の場合は稀だとコンパイラに伝える（clang と gcc）」。ヘッダー 1 か所の変更で、遅延化の動作もメモリの削減も変わらない。

| サンプル（描画なし、交互に 10 回） | パッチなし | 変更前 | 変更後 | 検査なしの下限 |
|---|---:|---:|---:|---:|
| シミュレーション 1 フレームの平均、最良値（ms） | 6.61 | 6.88 | 6.48 | 6.21 |
| 同じラウンドの下限との比 | −0.5% | +4.9% | +1.2% | — |
| うち知覚 | −0.7% | +11.4% | +2.2% | — |

- サンプルでは、変更後は下限ともパッチなしとも雑音の幅で並ぶ（この回は PC 全体が遅く、変更前の差も +5〜6% だった）。ワーキングセットの削減は変更前と同じ。
- **残る費用**: ほかのジェネリックへ渡すだけの小さいメソッド（`Repository<T>` の添字が `List<T>` の添字を呼ぶ、など）。空の時に解決の関数を呼ぶ経路があるだけで、引数を保つための退避と復帰が入る（MSVC で 11 命令 → 23 命令）。`repo.item` は、パッチなし 2.59、変更前 3.64、変更後 3.48 ns。`list.capacity` は 0.98 → 0.73 ns でパッチなしに戻る。
- **arm64 の単体の試験**（`speed/rgctx-read.sh`。Pixel 3 XL、NDK の clang。Player ではなく、ループだけを取り出したもの。1 サイクルが約 0.36 ns で、コードの配置で ±1 サイクル動く）:

| 1 項目あたりの ns | パッチなし | 変更前 | 1 回だけ読む | ＋空は稀と指定 | ＋解決の関数がレジスタを保つ |
|---|---:|---:|---:|---:|---:|
| ループ（読み出し 2 回と呼び出し 2 回）、`-Os` | 2.95 | 4.29 | 3.57 | 3.57 | 3.57 |
| 同、`-O3` | 3.21 | 3.22 | 3.57 | 3.22 | 3.21 |
| 渡すだけのメソッド（読み出し 1 回）、`-Os` | 2.86 | 4.22 | 4.19 | 4.19 | 3.57 |
| 同、`-O3` | 2.50 | 4.20 | 4.15 | 4.16 | 3.57 |

- ループの中の読み出しは、`-O3`（iOS の既定）ではパッチなしと並ぶ。渡すだけのメソッドは、arm64 でも 1 回あたり 1.3〜1.7 ns 残る。解決の関数に「呼び出し側のレジスタを保つ」指定（`preserve_most`）を付けると 0.7〜1.1 ns になるが、0 にはならず、iOS で確かめられないので製品には入れていない。
- 残りを消すには、検査そのものを無くす対象を選ぶ必要がある（特定のジェネリックの定義だけ先に全部解決して、その共有コードでは検査なしで読む）。検査は共有コードの中にあるので、定義ごとに分けるには生成された C++ の書き換えが要る。試していない。
- 確かめたこと（Windows x64）: 検証 6 種、競合を含むリフレクションの検証の繰り返し 20 回、型あたりのメタデータの量が 5 パターンで変更前と一致すること、`Il2CppLazyMetadataCheck.Run`。
- 確かめたこと（Android の実機、2026-11-14。コミットした時点では未実行だった）: 直したランタイムの計測用 Player（`e-v8-v1`）で検証 6 種が通る。直す前（`e-v6-base`）と交互に 5 ラウンド測ると、RGCTX を読むカーネルが速くなり、遅くなったものは無い（`util.safeget` 7.04 → 6.39、`repo.get` 40.1 → 38.2、`repo.item` 10.21 → 9.95、`itf.dict.tryget` 46.2 → 43.6 ns）。サンプルでの値は下の「端末での計測」。

### FPS で見た時（同期待ちを当てはめる。2026-11-14、Windows x64）

画面の更新に合わせて表示する環境では、フレームが予算（60 fps で 16.7 ms、30 fps で 33.3 ms）に収まっている間は、処理が数 % 遅くなっても FPS は変わらない。差が出るのは予算の近くにいる時で、はみ出したフレームは次の更新まで待つので 2 倍の長さになる。

サンプルを描画つきで動かし、1 フレームごとの時間（`-workload-series 1`）に同期待ちを当てはめた（`.local/w/w-fps.py`。各フレームを、できあがった後の最初の更新で表示するとした時の FPS と、予算を超えたフレームの割合。3 回の中央値）。

| 体数 | 条件 | 1 フレームの平均（ms） | 30 fps 目標 | 60 fps 目標 |
|---:|---|---:|---:|---:|
| 1,000 | パッチなし／変更前／変更後 | 5.6／5.3／6.2 | 28.9／29.6／28.9 | 55.9／58.5／55.8 |
| 2,000 | パッチなし／変更前／変更後 | 10.0／12.0／9.7 | 30.0／29.3／30.0 | 57.8／51.8／58.7 |
| 3,000 | パッチなし／変更前／変更後 | 14.5／15.6／15.5 | 30.0／30.0／30.0 | 49.1／46.3／45.6 |
| 4,000 | パッチなし／変更前／変更後 | 22.4／24.8／23.2 | 27.5／25.9／27.1 | 32.0／29.1／30.8 |
| 6,000 | パッチなし／変更前／変更後 | 35.0／40.6／35.4 | 19.8／16.5／19.4 | 23.5／20.2／23.3 |

- 予算に余裕がある所（1,000 体の 60 fps、3,000 体までの 30 fps）では、3 条件とも目標に張りつき、差が無い。
- 予算の近くでは、検査を直す前のパッチが FPS を落とす。2,000 体の 60 fps で 57.8 → 51.8（はみ出すフレームが 3.8% → 11.0%）、4,000 体の 30 fps で 27.5 → 25.9、6,000 体の 30 fps で 19.8 → 16.5。
- 直した後は、2,000／4,000／6,000 体でパッチなしと並ぶ。3,000 体の行は 3 条件の順が入れ替わっていて、3 回では読み取れない（同じ条件でも 1 回ごとに ±10% 動く）。
- 1,000 体で 30 や 60 に届いていないのは、描画側の 1 回きりの準備（計測の区間に約 500 ms のフレームが 1〜2 回入る）の分で、条件の差ではない。
- この表は PC での値で、端末とは同じ体数での FPS そのものが違う。端末での値は下の節。

### 端末での計測（2026-11-14、Pixel 3 XL、arm64、`-Os`、画面は 60 Hz）

サンプルを Android 用に、パッチなし／検査を直す前のパッチ／直した後のパッチの 3 本でビルドして、交互に測った（`.local/w/w-android-build.sh`、`w-android-run.py`）。端末の計測はばらつきが小さい（同じ条件で ±0.3%）。状態のチェックサムと出来事の数は、端末でも 3 条件で一致した。

**シミュレーションの時間**（2,000 体、描画なし、5 ラウンド。1 フレームの平均）:

|---|---:|---:|---:|
| 中央値（ms） | 12.94 | 13.22 | 13.03 |
| 同じラウンドのパッチなしとの比 | — | +2.0% | +0.9% |
| うち移動と衝突 | — | +4.4% | +2.7% |
| うち知覚 | — | +1.9% | +1.2% |
| うち戦闘 | — | −2.5% | −2.5% |

- **arm64（clang）では、パッチの代償は直す前で +2.0%、直した後で +0.9%。** 5 ラウンド全部で同じ向きだった。Windows（MSVC）の +6〜11% は、MSVC が読み出しを関数呼び出しにしていた分が大きい。

**実際の FPS**（描画つき、3 ラウンドの中央値。1 秒あたりに作れたフレームの数）:

## コンパイラの指定、SIMD、エンジン呼び出しの実測（2026-11-13、Pixel 3 XL、arm64）

ここから採用を決めたものはない。判断の材料として数値を残す。条件を 5 ラウンド交互に測った中央値（数値のベンチは最良値）で、ランタイムは遅延化だけを入れたもの。道具は `e-android-build.sh`、`e-android-run.py`、`e-stats.py`。

### コンパイラの指定

- 渡し方は `PlayerSettings.SetAdditionalIl2CppArgs("--compiler-flags=-O3")`。フラグ 1 つにつきオプションを 1 つ書く（カンマでつなぐと 1 つのフラグとして扱われる）。既定の `-Os` の後ろに付いて、後ろが勝つ。
- Android は Debug 以外で `-Os`、LTO なし。iOS は `-O3`、LTO なし（Editor のビルドの DLL を読んだ結果で、iOS ではビルドしていない）。

| 指定 | libil2cpp.so | ビルド時間 | 既存のカーネル 41 本 |
|---|---:|---|---|
| `-O2` | +3.6% | 変わらず | LINQ の重い方 −5%、キャスト +4〜12% |
| `-O3` | +11.0% | 変わらず | 速い 7、遅い 8、±2% 以内 24 |
| `-O3` と `-flto=thin` | +29.5% | 約 2 倍 | 速い 22（`list[i]` −43〜−56%、`IList<T>` 経由 −23〜−41%）、遅い 5、±2% 以内 13 |
| `-O2` と `-flto=thin` | +16.7%（キャッシュ入りのランタイムでの比較。79.7 → 93.1 MB） | 約 2 倍（20 分 18 秒） | 速い: `list[i]` −36〜−56%、`IList<T>` 経由 −22〜−43%、共有コード経由の読み出し −12〜−64%、LINQ の重い方 −13%。遅い: インターフェースへのキャスト +33〜37%、配列の添字ループ +10%（2026-11-14 に計測。ラベルは `e-v5-o2lto`） |

- `-O2` と ThinLTO の組でも、`list[i]` のループから `get_Item` の呼び出しが消える（逆アセンブルで確認）。ファイルをまたぐインライン化は `-O3` でなくても効く。配列を添字で回すループは、`-O3` と同じ「範囲検査のない詰まった形」になる。
- `-O2` と ThinLTO の実測（2026-11-14、キャッシュ入りのランタイムで `-Os` と交互に 5 ラウンド。結果は `results/e-h1`）: 検証 5 種が通る。得は `-O3` との組とほぼ同じで、配列の添字ループの遅れは +55% でなく +10%（2.27 → 2.45〜2.51 ns）で済む。代わりに、**キャストのキャッシュを通るインターフェースへのキャストが 16.1 → 21.4 ns（+33〜37%）に遅くなる**。原因は調べていない（キャッシュを入れたランタイムを ThinLTO で測ったのはこれが初めて）。数値のベンチでは、検査なしの C# のループがベクトル化される（`saxpy` と int の合計で −62%）。
- 配列を添字で回すループが、`-O3` と ThinLTO で 55% 遅くなる（2.31 → 3.6 ns）。`-O2` では出ない。**原因は確定していない。** 分かったこと（`speed/array-walk.sh`。同じループを端末で単体で測る）:
  - `-O3` のコードは仕事が減っている。範囲検査が消え、1 要素あたり 10 命令から 7 命令になる。パス 16 回分が丸ごと展開されるが、展開は速さに関係しない（1 つのループを 16 回まわす形と同じ速さ）。
  - Player の 2 つのループの機械語をそのまま単体で測ると、どちらが速いかは、要素のオブジェクトの並び方で入れ替わる。詰まって並ぶ時（32 バイト間隔）は `-O3` の形が 22% 速く、64〜192 バイトの等間隔では 12〜23% 遅く、不規則な並びでは 3〜9% 速い。配列そのものがキャッシュに収まる大きさなら差が無い。
  - Player での実際の並び（`SpeedBench` が結果の `layout` の行に書く）は、アドレスが 48 バイトずつ下がっていく並びだった（1,024 個のうち 992 個の間隔が −48 バイト）。この並びを単体の試験で再生すると、`-Os` の Player のループは 2.26 ns（Player での実測 2.29 ns と一致）、`-O3` の Player のループは 3.08〜3.10 ns（Player では 3.59 ns）になる（2026-11-14）。**遅れは「`-O3` の詰まったループ」と「このオブジェクトの並び」の組み合わせで再現する。** 同じ C++ を単体でコンパイルした `-O3` の版（範囲検査が 1 つ残る 8 命令のループ）は 2.26 ns で、遅くならない。
  - 計測中の Player のメインスレッドは、`-Os` でも `-O3` でも大きいコアで動き、周波数は最大（2.80 GHz）だった。コアや周波数の違いではない。
  - 再現できたのは +36% で、Player の +57% との差（3.1 対 3.6 ns）は説明がついていない。なぜこの組み合わせで遅くなるか（プリフェッチやキャッシュの挙動）までは調べていない。配列の添字ループ一般の話ではなく、このカーネルのデータの並びに依存する現象として扱う。
- 起動時間は変わらない。検証 5 種は、計測した 4 条件の全部で通る（各 1 回）。`-O2` と ThinLTO の組み合わせは、その後に検証も計測もした（上の表の 4 行目と、「最終結果」。全部入りの Player で検証 6 種が通る）。

### SIMD と演算（4,096 要素、1 要素あたりの ns）

| 処理 | C# `-Os` | C# `-O3` | 検査なしの C# `-O3` | Burst | NEON の手書き |
|---|---:|---:|---:|---:|---:|
| int の合計 | 1.073 | 0.135 | 0.135 | 0.138 | |
| float の合計 | 1.072 | 1.069 | 1.069 | 1.070（`FloatMode.Fast`: 0.139） | 0.113 |
| y に a×x を足す | 2.148 | 1.672 | 0.230 | 0.249 | |
| コピー | 1.431 | 0.174 | 0.190 | 0.274 | |

- 既定の `-Os` では、C# にも C++ にも自動のベクトル化が 1 つも入らない（逆アセンブルで確認）。
- float の合計は指定では速くならない（足す順序を変えられないため）。範囲の検査が残るループは `-O3` でもベクトル化されず、`[Il2CppSetOption]` で検査を外すと入る。

- sqrt と整数の割り算は、どの手段でも変わらない。

### エンジン呼び出し（自動の書き換えで削れる余地）

Player に入るコード（エンジンとクラスライブラリを除く 38,630 メソッド）を IL から数えた。エンジンを呼ぶ箇所は 2,141、うちループの中は 295。中身はこのプロジェクトのライブラリ、サンプル、URP、UI、Input System で、ゲーム本体のコードではない。

- 呼び出しを規則で消す書き換え（ループの外へ出す、読み直しを消す、2 回を 1 回の API にまとめる）が当てはまるのは 56 か所（2.6%）だけ。
- 数値や構造体をやり取りする呼び出しの橋渡しは最小に近く、`-O3` でも ThinLTO でも変わらない。
- 余地があるのは 2 か所。エンジンのオブジェクトの null 比較（1,121 か所）は 10.1 → 2.3 ns（参照だけの比較は 1.4 ns）。オブジェクトを返す呼び出し（490 か所）の受け取りは、まねた経路で 13.4 → 6.4 ns で、呼び出し全体（42〜54 ns）の 13〜17%。null 比較は IL の段階 `nulltest` にした（上の節）。受け取りの方は実装していない。
- 1 回の時間: static の getter 約 5 ns、数値を返す getter 8.6 ns、構造体を返す getter 38.6 ns（同じオブジェクトの 2 回目以降は約 10.7 ns）、親が 4 段ある `position` 96.9 ns とその代入 134.4 ns、`name` 401 ns、`GetComponent<T>` 340 ns。大半はエンジンの中の時間。
- エンジンが返すハンドルは強参照で、ロックを通る経路はない。
