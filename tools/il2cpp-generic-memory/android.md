# Android での推奨: 下位の端末まで支えるゲームに、どこまで入れるか

Android の下位の端末まで支えるゲーム（UI とロジックが中心のソーシャルゲームを想定）に、この作業の最適化のうちどれを入れるかをまとめる。数値の元は [README.md](README.md) の「最終結果」（2026-11-14、Pixel 3 XL）である。**実測と見積もりを分けて書く。** 「見積もり」の節は計測ではない。

## 結論

入れるのは 2 つ。遅延化のパッチと、コンパイラの指定である。UniTask を使うコードなら、ステートマシンの寄せも入れる。

| 対策 | 推奨 | 得るもの | 払うもの |
|---|---|---|---|
| 遅延化のパッチ（キャストのキャッシュなし） | **入れる** | 型あたりのメタデータが 16 パターンの合計で −65%。型の初回利用が 3〜8 倍速い | C# の処理が +1.0%。Android には自動で当てる仕組みが無い |
| `-O2` と `-flto=thin`（リリースのビルドだけ） | **入れる** | C# の処理が −6.1% | libil2cpp.so が +20%、ビルド時間が約 1.4 倍 |
| UniTask のステートマシンの寄せ | UniTask を使うなら入れる | async メソッド 1 本あたり 6.5 → 0.68 KB（Windows での値） | 効果を端末では測っていない |
| キャストのキャッシュ | 入れない | ジェネリックなキャストが 3〜15 倍速い | 全体の時間は動かない。ジェネリックでないキャストの当たる形が遅くなる |
| IL の段階（`comparers+enum+linq+nulltest`） | 後回し | メタデータが合計で −65% → −75% | 製品としての入れ方が無い。DLL を書き換える |

- **メモリを減らすのはパッチで、全体の速度を上げるのはコンパイラの指定である。** 2 つは別々に効く。
- 下位の端末で先に効くのはメモリの方である。速度の得は、フレーム全体では数 % にとどまる（下の「見積もり」）。
- **推奨の組（パッチと指定の 2 つだけ）そのものは、ビルドも計測もしていない。** 測ったのは、それぞれ単独と、全部入りである。

この資料で「C# の処理」の時間は、サンプル（2,000 体の AI）のシミュレーション 1 フレームの時間を指す。描画を含まない、ほぼ C# だけの処理である。

## 計測の条件

- 端末: Pixel 3 XL（2018 年、Snapdragon 845、arm64、Android 12、画面は 60 Hz）。メインスレッドは大きいコア（Cortex-A75）で動いていた。
- Unity 6000.3.20f1、IL2CPP、arm64 だけ、IL2CPP Code Generation は Faster runtime、Managed Stripping は High、APK。
- Android の既定のコンパイルは `-Os` で、LTO なしである。
- 測ったもの: ゲームに近い負荷のサンプル（2,000 体の AI。リポジトリの外）と、計測用の Player のカーネル。条件を交互に走らせ、同じ巡のパッチなしとの比で読む。
- 確かめたこと: サンプルののべ 122 回の実行で、状態のチェックサムと出来事の数が、体数ごとに全部一致した。計測用の Player は、パッチなし、遅延化だけ、全部入りの 3 本で検証 6 種が通る。計測中に、温度による周波数の制限は一度もかからなかった。

## 実測（Pixel 3 XL）

### サンプル

| 構成 | シミュレーションの時間 | FPS（2,000 体） | FPS（3,000 体） | プロセスのメモリ | libil2cpp.so | APK | ビルド時間 |
|---|---:|---:|---:|---:|---:|---:|---:|
| パッチなし | 12.94 ms | 55.6 | 35.8 | 229.0 MB | 52.5 MB | 30.7 MB | 10:49 |
| 遅延化のパッチ | +1.0% | 55.1 | 35.4 | −9.3 MB | 56.4 MB | 31.9 MB | 9:43 |
| ＋キャストのキャッシュ | +1.0% | 55.1 | 35.4 | −9.2 MB | 56.4 MB | 31.9 MB | 8:48 |
| ＋IL の段階 | +0.5% | 55.0〜55.3 | 35.4〜35.5 | −9.0〜−9.5 MB | 56.2 MB | 31.9 MB | 8:38 |
| ＋`-O2` と `-flto=thin`（全部入り） | −4.9〜−5.1% | 58.2〜58.3 | 37.9 | −9.6〜−9.7 MB | 66.4 MB | 34.5 MB | 15:46 |
| パッチなし＋`-O2` と `-flto=thin` | −6.1% | 58.9 | 38.7 | −0.6 MB | 63.2 MB | 33.3 MB | 14:42 |

- 「遅延化のパッチ」の行は、メモリのブランチ（`il2cpp-generic-memory`）のパッチで測った。キャストのキャッシュのコードを持たない形である。
- 1,500 体では、`-Os` の 4 構成とも 59.9 fps で差が無い。差が FPS に出るのは、目標の FPS を保てない規模だけである。
- ThinLTO を入れても、パッチの費用は残る。同じ ThinLTO どうしで比べると、全部入りはパッチなしよりシミュレーションが 1.5%（描画なし）、2.0〜3.2%（描画つき）遅い。
- プロセスのメモリは、起動から 25 秒後の PSS の合計である。ThinLTO の構成では、約 15 MB が無名のメモリからライブラリの側へ移る（パッチなしでも同じ）。内訳は調べていないので、合計だけで読む。

### 型あたりのメタデータと、型の初回利用

- 型あたりのメタデータ（2026-11-12 の端末での計測）: 16 パターンの単純な合計で、553.5 KB → 遅延化で 195.7 KB（−65%）→ IL の段階を重ねて 136.8 KB（−75%）。60% 以上減るパターンは、16 のうち 9、IL を重ねて 13 である。届きにくいのは、Task、UniTask、デリゲートのパターン（−16〜−53%）。
- 型 200 個の初回利用: `List` を使う形で 320 → 79 ms、`Dictionary` で 245 → 82 ms、重い LINQ で 1,261 → 368 ms、利用者のジェネリッククラスで 567 → 74 ms。3〜8 倍速い。
- 起動から結果までは 3,196 → 3,074 ms（−4%）。

### 遅延化のパッチで遅くなる操作

- RGCTX を読む小さいメソッド: ほかのジェネリックへ渡すだけのメソッドが 6.40 → 10.05 ns（+57%）、`Repository<T>.Get` が +16%、`List<T>.Find`（100 要素）が +18%。
- 変性つきのインターフェース呼び出しが 124.8 → 142.1 ns（+14%）、`List<T>` を `IList` として判定する形が 15.4 → 21.0 ns（+37%）。
- arm64 では、ジェネリックなインターフェースへのキャストは、パッチだけでもパッチなしより速い（同じ型で −22%、失敗する形で −25%）。

## 見積もり（計測ではない）

### 推奨の組での値

パッチ（キャッシュなし）と `-O2`＋ThinLTO の 2 つだけを入れた Player は作っていない。上の表から次のように見積もる。

| | 見積もり | 元にした値 |
|---|---|---|
| シミュレーションの時間 | −3〜−5% | 指定だけの −6.1% が上限。そこからパッチの費用を引く |
| プロセスのメモリ | −9〜−10 MB | パッチの −9.3 MB と、全部入りの −9.6〜−9.7 MB |
| libil2cpp.so、APK | +26% 前後、+12% 前後 | 全部入りの値 |
| ビルド時間 | 約 1.5 倍 | 全部入りの値。計測用の Player では 2.3 倍だった |

- ThinLTO の下でのパッチの費用は、キャッシュと IL の段階を重ねた構成でしか測っていない（+1.5%）。その構成の `-Os` での費用は +0.5% で、パッチだけの +1.0% の半分だった。パッチだけなら +1.5% より大きい可能性があるので、+1.5〜3% として幅を取った。

### フレーム全体への影響

上の比は C# の処理だけの値である。エンジンのネイティブコードと GPU は、どの対策でも変わらない。フレーム全体への影響は、「フレームの CPU 時間のうち C# が占める割合 × 上の比」になる。

UI とロジックが中心のゲームを想定して、C# の割合を 4〜6 割と仮定する。

| | C# の処理 | フレームの CPU 時間（仮定の下で） |
|---|---:|---:|
| 遅延化のパッチ | +1.0% | +0.4〜0.6% |
| `-O2` と `-flto=thin` | −6.1% | −2.4〜−3.7% |
| 推奨の組 | −3〜−5% | −1〜−3% |

- 目標の FPS を保てている端末では、この差は FPS に出ない。
- 目標を割っている端末では、この割合だけ FPS が動く。25 fps なら 25.3〜25.8 fps である。目標から大きく離れた端末を救う大きさではない。
- サンプルはほぼ C# だけで動く。サンプルの FPS の差（指定だけで +5.9〜7.9%）は、有利な側の値である。

### 下位の端末（小さいコアだけの SoC）

- 全体の計測は、大きいコア（Cortex-A75）でのものしか無い。小さいコア（Cortex-A55）で測ったのは、RGCTX の読み出しの単体の試験だけである。
- その試験では、パッチの検査の割合は、小さいコアの方が小さかった（ループで +9% 対 +21%、渡すだけのメソッドで +21% 対 +50%）。**パッチの費用の割合は、下位の端末で大きくはならないと見る。**
- 同じ試験で、小さいコアは大きいコアの 3〜4 倍遅かった。型の初回利用の時間も、同じ程度に伸びると見る。新しい型を 100 個初めて使う画面なら、大きいコアで 0.12〜0.16 秒が 0.04 秒になる（`List` と `Dictionary` の実測の半分）。小さいコアでは、0.4〜0.6 秒が 0.15 秒前後になる計算である。
- ThinLTO の得が小さいコアでどう変わるかは、データが無い。

### メモリ

- プロセス全体でどれだけ減るかは、ジェネリックに入れる型（`List<Foo>` の `Foo`）の数と、その使い方で決まる。サンプルはそういう型が少なく、−9.3 MB（−4.1%）だった。
- 16 パターンでは、ジェネリックに入れる型 1 つあたり、約 20 KB 減る（差の中央値が 21 KB、平均が 22 KB。幅は 0.4〜77 KB）。そういう型が 1,000 個なら約 20 MB、3,000 個なら約 60 MB 減る計算になる。使い方の混ざり方で変わる。
- この単位は、パターンに通す型 1 つである。1 つの型は、ふつう複数の具象クラス（リスト、その列挙子、インターフェース）を作る。Player の中の具象クラスの数で数えると、多く見積もりすぎる。
- メタデータのバイト数は、Windows x64 と Android arm64 で 16 パターンとも同じだった。64 ビットなら、端末によらず同じ量が減ると見る。

## 入れないものと、見直す条件

### キャストのキャッシュ

- サンプル全体の時間は、キャッシュありでもなしでも +1.0% で、同じだった。
- 速くなるのは、ジェネリックなインターフェースへのキャスト（53〜239 ns → 16 ns）と、変性つきのインターフェース呼び出し（125 → 29 ns）。
- 遅くなるのは、ジェネリックでないキャストの当たる形（14.5 → 16.1 ns、+11%）。外れる形は速くなる（21.5 → 16.5 ns）。
- ThinLTO と重ねると、キャッシュを通るキャストが 16 → 22 ns になる。ジェネリックでないキャストの当たる形は、パッチなしより 47% 遅い。原因は調べていない。
- **見直す条件**: ジェネリックなインターフェースへのキャストや、変性つきの呼び出しが多いコード。サンプルでは、そういう段階（意思決定、戦闘）がパッチなしより 2〜3% 速くなった。

### IL の段階

- メタデータは、16 パターンの合計で −65% → −75%。`List`、配列、LINQ を使う形に効く（`List` を使う形で 10.3 → 4.7 KB）。
- サンプルでは、プロセスのメモリは変わらず（−9.0〜−9.5 MB）、シミュレーションの時間は +1.0% → +0.5% だった。
- 段階 `nulltest` は、エンジンのオブジェクトと `null` の比較を 10.3 → 1.95 ns にする。
- 製品としての入れ方が無い。計測用のビルドが、UnityLinker の前に全部の DLL を書き換える形で入れた（`GenericMemoryPreLink.cs`）。
- 段階 `linq` は、LINQ の 1 回あたりの GC のバイト数を 1〜7% 増やす。
- **見直す条件**: パッチを入れても、メモリが足りない時。

## UniTask を使う場合

- `Assets/UniTaskStateMachinePool` は ILPostProcessor で、UniTask を参照するアセンブリの Player のコンパイルで走る。Android のための特別な経路は要らない。
- 効果を測ったのは Windows だけである。async メソッド 1 本あたりのメタデータが 6.5 → 0.68 KB になり、中断時の確保は 0 のままだった。
- 遅延化のパッチは、UniTask のパターンには −37% しか届かない。async の多いコードでは、こちらが効く。
- この資料の実測の表の差には、この書き換えの効果は入っていない。外す定義（`UNITASK_STATE_MACHINE_POOL_OFF`）を付けたビルドが無く、どの Player も同じ条件のはずだからである。端末のビルドで、書き換えた件数は確かめていない。
- 計測用の Player の async の検証 66 件は、端末でも通っている。

## 入れ方

### コンパイラの指定

`PlayerSettings` の追加の引数で渡す。この設定はプラットフォームごとではないので、Android のリリースのビルドの間だけ置いて、終わったら戻す。

```csharp
var before = PlayerSettings.GetAdditionalIl2CppArgs();
PlayerSettings.SetAdditionalIl2CppArgs("--compiler-flags=-O2 --compiler-flags=-flto=thin");
try
{
    BuildPipeline.BuildPlayer(options);
}
finally
{
    PlayerSettings.SetAdditionalIl2CppArgs(before);
}
```

- フラグ 1 つにつき、オプションを 1 つ書く。カンマでつなぐと、1 つのフラグとして扱われる。
- 既定の `-Os` の後ろに付いて、後ろが勝つ。
- 環境変数 `IL2CPP_ADDITIONAL_ARGS` は、C++ のコンパイルに届かなかった。
- リンカーへの指定は足していない。この 2 つだけで、ファイルをまたぐインライン化が効く（`list[i]` のループから `get_Item` の呼び出しが消えることを、逆アセンブルで確かめた）。
- 計測では、指定が全部のコンパイル単位に付いたことを、ビルドの記録から確かめた（`e-android-keep.py`）。
- `-O2` だけでは得が小さい（重い LINQ で −5%、キャストは +4〜12%）。`-O3` と ThinLTO の組は、配列の添字ループが 55% 遅くなった（`-O2` との組では +10%）。カーネルの計測では、得のほとんどが ThinLTO の側から来る。

### 遅延化のパッチ

Android には、パッチを自動で当てる製品のコードが無い。`Il2CppLazyMetadata.cs` の `OnPostprocessBuild` は、iOS のビルドでだけ動く。計測では次の形を使った。Editor のインストール先は書き換えない。

1. Editor の `Data/il2cpp` の複製を作る。2 つ目からは、`libil2cpp` だけ実体を複製し、ほかのフォルダは最初の複製へのジャンクションにする（`kit/make-copy.sh`）。
2. 複製の配置を、開発用の配置に合わせる。`UNITY_IL2CPP_PATH` を置くと、Unity はその配置を要求する（[record.md](record.md) の `UNITY_IL2CPP_PATH` の説明）。
3. 複製の `libil2cpp` にパッチを当てる。当てるのは `Il2CppLazy.Il2CppLazyMetadata.Apply` である。
4. Player のビルドの間だけ、Editor のプロセスに `UNITY_IL2CPP_PATH=<複製>` を置き、`finally` で必ず外す（`GenericMemoryAndroidBuild.cs`）。残すと、Editor 自身のスクリプトのコンパイルが同じ場所を見て止まる。
5. どの libil2cpp がコンパイルされたかを、ビルドの記録で確かめる（`d-android-keep.py`）。

- **キャッシュなしの形**: 実測の行は、メモリのブランチのパッチで測った。このブランチ（`il2cpp-speed`）の `Apply` は、既定でキャストのキャッシュも入れる。外すには 3 つ目の引数を偽にする（`Apply(root, false, false)`）。この形は、キャッシュの行がコンパイルで消えるだけの違いだが、端末では動かしていない。測ったものと同じにするなら、`il2cpp-generic-memory` のパッチを使う。
- 環境変数 `IL2CPP_CAST_CACHE=0` を読むのは、iOS のビルドの後の処理だけである。
- Unity の版を上げたら、`Il2CppLazyMetadataCheck.Run(null)` で、パッチがその版の libil2cpp に当たるかを確かめる。差し込む先の文面が変わっていれば、`Apply` は当てずに止まる。複製は作り直す。

### UniTask のステートマシンの寄せ

`Assets/UniTaskStateMachinePool` をプロジェクトに置くだけで、Player のコンパイルで走る。Editor のコンパイルと、`UNITASK_STATE_MACHINE_POOL_OFF` を定義したビルドは書き換えない。

## 確かめていないこと

- 推奨の組（パッチと指定の 2 つだけ）のビルドと計測。
- 小さいコアだけの端末での、全体の計測。
- 32 ビット（ARMv7）。計測用のビルドは、arm64 だけの設定でしか動かない。
- AAB、Gradle プロジェクトの書き出し、Managed Stripping の High 以外、IL2CPP Code Generation の Faster (smaller) builds。
- 実際のゲームでの値。測ったのは、サンプルと計測用の Player である。
- Pixel 3 XL 以外の端末、Android 12 以外の版、ページの大きさが 16 KB の端末。
- 長い時間の実行での、熱と電池への影響。
- UniTask の寄せの、端末での効果。
- ThinLTO で、キャッシュを通るキャストが遅くなる原因。
